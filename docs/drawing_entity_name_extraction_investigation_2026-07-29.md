# 図面名称未抽出の調査結果

調査日: 2026-07-29

## 結論

名称未抽出は単一原因ではない。共有対象ICD 39件を現在の製品・装置・ユニット／部品payloadで横断確認した結果、主因は次の6点だった。

1. 部品名称として有力な `top_part.comment` を抽出済みなのに、画面の名称決定では使わず備考へ送っている。一方、製品・装置・ユニットでは禁止対象の `top_part.name` を名称フォールバックに使っている。
2. 2D図枠の名称抽出が「ラベルと値が同じ文字要素内、または同じ文字payloadの次行」に限られ、別文字要素の値を名称候補にできない。
3. ICADネイティブ2D抽出で、DXFには存在する文字が0件になる図面がある。SXNETのセグメント種別と `getGeomList()` のnull内訳を記録していないため、現在のJSONだけでは取りこぼした要素種別を確定できない。
4. ICADから取得できた生文字の約48%を、印刷範囲の信頼判定で名称解析前に捨てている。生文字があるのに信頼対象が0件になる図面もある。
5. 部品名辞書は22個の一般語だけで不足しているうえ、辞書照合前にNFKC正規化をしていない。登録済みの `BRACKET` も全角 `ＢＲＡＣＫＥＴ` には一致しない。
6. 保存データ自体のUTF-8破損は確認されなかった。見かけ上の文字化けは、仮想環境Pythonの標準出力コードページと受け側の不一致、およびiCADフォント依存の私用領域文字を分けて扱う必要がある。

`top_part.name` は図番・ファイル名相当の識別子であり、製品・ユニット名または部品名として使用してはならない。今回の改善候補にも含めない。

## 横断集計

対象は `output/souya_handoff/icad_extract_import_manifest_all_shared_2026-07-15.json` の39件。

| 対象 | 件数 | 現在の名称表示 | 2D `drawing_name` | `top_part.comment` |
| --- | ---: | --- | ---: | ---: |
| 部品 | 33 | `名称未抽出` 28件、辞書語5件 | 0件 | 22件 |
| 製品・装置・ユニット | 6 | 全6件がファイル名／識別子相当 | 0件 | 1件 |

部品の `名称未抽出` 28件のうち20件には `top_part.comment` が存在した。

名称らしい実例:

- `217008-41J-3004.icd`: `レール`
- `32791729A01.icd`: `ワッシャ`
- `36555211A01.icd`: `ジョイント`
- `6051033A.icd`: `ノズルブラケット`
- `CAA5012-02434006P1R1.icd`: `プレート`
- `CAA5012-02435010P1R1.icd`: `押サエブロックブラケット2`
- `G1630-S3000-039_A0a1.icd`: `ﾃｰﾙｽﾄｯｸﾎﾝﾀｲﾍﾞｰｽ`
- `PSG011-PA13002.icd`: `制御盤BOX架台`

一方、次のようなコメントもあるため、`top_part.comment` の無条件採用は禁止する。

- 図番だけの参照情報
- `...を変更` のような変更元説明
- 名称か用途・状態かを自動確定できない語

したがって `top_part.comment` は「名称候補」として保持し、名称らしさの検証と根拠表示を通したものだけを確定名称にする必要がある。

## 原因1: 抽出済み3Dコメントが名称決定から外れている

`PartTreeFlattener` は `SxInfPart.name` と `SxInfPart.comment` を別々に抽出している。

- `name`: 識別子、図番、モデル名寄り
- `comment`: 部品名・組立名が入る例が多い

正規化後も `top_part_comment` として保持されるが、`icad_entities._build_record()` では名称候補に使われず、`remarks` へ入るだけである。

部品名称は現在 `drawing_name` と部品名辞書一致だけから選ばれる。これが、コメントを抽出できている20件まで `名称未抽出` になる直接原因である。

製品・装置・ユニットでは逆に、`drawing_name` が無いと `top_part.name`、3D部品名、ファイル名の順にフォールバックする。共有6件がすべてファイル名／3D最上位識別子相当になっているため、この分岐は「3D最上位名を名称として使わない」という要件に違反している。

## 原因2: 2D名称欄の値取得条件が狭い

現行の図枠抽出は、1つの文字payloadごとに処理する。

- `品名: 開口カバー`: 取得できる
- 同じ文字payload内の `品　名` の次行に `開口カバー`: 取得できる
- `品　名: 開口カバー` のようにラベル内に空白がある: ラベルは検出するが値を切り出せない
- `品　名` と `開口カバー` が別文字要素: 取得できない

再現結果:

| ケース | 現行 `drawing_name` |
| --- | --- |
| `品名: 開口カバー` | `開口カバー` |
| `品　名: 開口カバー` | 未抽出 |
| 同一payloadの次行 | `開口カバー` |
| 別文字要素 | 未抽出 |
| `UNIT Name` ラベルだけ | 誤って `UNIT` |
| `MACHINE Name` ラベルだけ | 誤って `MACHINE` |

空白入りラベルは `_normalize_for_match()` では一致するが、`_strip_label_value()` が元文字列上の直接一致に失敗した後、常に `None` を返すため値を切り出せない。

また `drawing_name` のキーワードに一般語 `name` があるため、`UNIT Name` や `MACHINE Name` のラベル部分を値として誤採用する問題も確認した。

## 原因3: ICADネイティブ2D文字の取得漏れ

共有39件のうちICADネイティブ2D文字が1件以上あるのは27件、0件は12件だった。

既にDXF変換済みの38件を照合すると、次の4件はICADネイティブ抽出が文字0件なのにDXFには文字が存在する。

| ファイル | ICADネイティブ文字 | DXF文字 |
| --- | ---: | ---: |
| `U8718-S71-002_A3.icd` | 0 | 19 |
| `U8718-S71-149_A4.icd` | 0 | 32 |
| `CAA5012-02430012P1R1.icd` | 0 | 133 |
| `CAA5012-02434006P1R1.icd` | 0 | 163 |

4件とも寸法・primitiveは取得できており、抽出ジョブもwarning 0で完了している。単なる「2Dなし」ではなく、現在の `SxVS.getSegList()` / `SxEntSeg.getGeomList()` 経路から文字要素が出てこない図面構造がある。

SXNET資料上、現行の6引数 `getSegList(0, int.MaxValue, true, true, true, true)` は、非表示要素、実像パーツ所属要素、検索対象外レイヤー、検索対象外種別をすべて含める指定であり、これらの真偽値で文字だけを除外しているわけではない。ただし資料では `num=0` が「offset以降の全要素」と明記されており、現行の `int.MaxValue` は実機比較対象に残る。

より大きな診断不足は、`getGeomList()` が未対応セグメントに返すnullを `ReflectionHelpers.Enumerate()` が黙って除外し、元セグメントの `SxInfEnt.type` を保存していない点である。そのため、文字が `SEGTYPE_TEXT` / `SEGTYPE_LBL` ではなく、シンボル・その他作図要素などに内包されているのかを現行結果から判定できない。次回Windows実機確認では、ビュー別の全セグメント件数、種別件数、null件数、文字・注記件数を抽出前後で記録する必要がある。

DXF 38件中、文字ありは30件、名称ラベル候補ありは10件だった。名称ラベルがあるだけで値が入っているとは限らないが、`23022-007_231218.icd` では `品名` 近傍に `(開口)` が存在するなど、ネイティブ抽出だけでは確認できない名称候補をDXF側で追える。

## 原因4: 印刷範囲フィルタで取得済み文字を捨てている

39件のICAD生文字は合計1,752件だった。現行の信頼判定を適用すると903件だけが残り、849件、約48%が名称解析前に除外される。

| 状態 | 図面数／文字数 |
| --- | ---: |
| 生文字0件 | 12図面 |
| 生文字あり・信頼対象0件 | 3図面 |
| 1件以上の文字を除外 | 20図面 |
| 生文字総数 | 1,752件 |
| 信頼対象文字 | 903件 |
| 除外文字 | 849件 |

生文字があるのに全件除外された図面:

- `47323200X40c.icd`: 10件 → 0件
- `CAA5012-02430002P1R1.icd`: 4件 → 0件
- `CAA5012-02435010P1R1.icd`: 3件 → 0件

`_is_usable_print_area_item()` は印刷枠が1件でも存在すると、`inside_print_area is True` 以外、すなわち外側だけでなく判定不明も捨てる。これは「ノイズを適切な文字だけに絞る」意図の実装だが、枠座標・ビュー座標・文字基準点のずれがある図面では正しい図枠文字まで失う。

生抽出は削除せず保持し、内側を第一候補、不明を低信頼候補、外側を原則除外とする段階評価へ変えるべきである。名称欄が見つからない場合は、不明領域まで再探索して根拠付きレビュー候補へ上げる。

## 原因5: 辞書不足と辞書照合前の正規化不足

有効な部品名辞書は22件で、`PLATE`、`COVER`、`BRACKET`、`BASE` 等の一般分類語だけである。固有の部品名称、複合名称、客先語彙、ユニット名称はほぼ含まれていない。

さらに `_match_dictionary_values()` はトークンと辞書候補を小文字化するだけでNFKC正規化しない。NFKCを監査上だけ適用すると、部品33件の辞書一致は5件から9件へ増え、次の4件が回復した。

- `03_20K03379P00_ｼｭｰﾄﾍﾞｰｽ(No.2FFS_XS).icd`: `BASE`
- `9NK5E51B70-00-BRACKET-A0-3D-01.icd`: `BRACKET`
- `9NK5E51M00-00-COVER-A3-3D-01.icd`: `COVER`
- `9NK5E56H20-00-BRACKET-A0-3D-01.icd`: `COVER`, `BRACKET`

ただし、`シュートベース` が `BASE` に縮退することや、図面内の注記を横断して複数一般語が一致することから、NFKC追加だけでは正式名称抽出にならない。辞書一致は部品種別・検索タグへ使い、図枠の名称欄や検証済み3Dコメントから得た完全な文字列を正式名称候補として別管理する必要がある。

## 原因6: 文字化け表示と保存データ破損を分けていない

選定39件のC#抽出JSONとDjango `raw_extract_json` を全1,752文字で比較した結果、文字列リストは全件一致した。U+FFFD、サロゲート、制御文字、典型的なUTF-8/CP932誤変換列も確認されなかった。詳細APIは厳格UTF-8でデコードでき、2D SVGも `image/svg+xml; charset=utf-8` で正常表示できた。

調査中に見えた `俹俙俼俿...` は、仮想環境PythonがWindows既定コードページで標準出力し、実行結果の受け側がUTF-8として解釈したために発生した。保存データの `ＰＡＲＴ　ＮＡＭＥ` は正常だった。標準出力を根拠に文字化け判定せず、JSONファイル、DB、HTTP応答のコードポイントで確認する必要がある。

一方、2図面5文字にはU+E30Eの私用領域文字が含まれていた。

- `PSG011-PA1100_クリーニング駆動.icd`: 3件
- `PSG011-PA0500_コラム.icd`: 2件

少なくとも前者はDXFにも同じ私用領域文字が残るため、単純な文字コード誤変換ではなくiCADフォント依存字形である。現行 `TextPayload` は `SxGeomText.atr_word.font` と `font_name` を保存しておらず、ブラウザ側が正しいフォントを選べない。生文字を勝手に置換せず、フォント種別・フォント名・コードポイントを証跡へ追加し、該当フォントを利用できない環境では「未解決字形」として表示する必要がある。

## 改善方針

### 1. 名称と識別子を分離する

- `top_part.name`: 3D最上位識別子。名称へ使わない
- `drawing_number` / `part_number`: 図番・部品番号
- `part_name`: 部品の正式名称
- `unit_name`: ユニット名称
- `equipment_name`: 装置名称
- `drawing_name`: 図面表題
- `name_candidates[]`: 未確定候補と根拠

製品・ユニットと部品で同じ `drawing_name` を使い回さない。

### 2. `top_part.comment` を対象別の名称候補へ上げる

無条件採用ではなく、次を除外・要確認にする。

- 値が図番形式だけ
- `変更`、`参照`、`元図` など変更元・参照元説明
- ファイル名または `top_part.name` と同一
- 空、記号だけ、文字化け

部品は `part_name_candidate`、製品・ユニットは `unit_name_candidate` または `equipment_name_candidate` として分ける。

### 3. 2D名称ラベルを対象別にする

一般語 `name` だけの照合をやめ、次の明示ラベルを別フィールドへ割り当てる。

- 部品: `品名`, `部品名`, `PART NAME`, `PARTS NAME`
- ユニット: `ユニット名`, `UNIT NAME`
- 装置: `装置名`, `MACHINE NAME`, `EQUIPMENT NAME`
- 図面: `図名`, `図面名`, `DRAWING TITLE`

空白入りラベルの値切り出しを修正する。

### 4. 別文字要素の対応は限定候補として実装する

汎用座標ペアリングで自動確定はしない。次の条件をすべて満たす場合だけ低～中信頼候補にする。

- 同じビュー、同じ印刷枠内
- 明示的な名称ラベル
- 値側がラベルや日付・図番・担当者でない
- 規定方向と距離範囲内
- 候補が一意
- ラベル・値双方の座標と原文を監査証跡へ保持

複数候補または客先図枠差がある場合は自動確定せずレビュー対象にする。

### 5. DXF文字を補完経路にする

次の場合にICADからDXFへ変換し、DXFの `TEXT` / `MTEXT` / `ATTRIB` を名称候補の補完元にする。

- ICADネイティブ文字が0件だが寸法・primitiveがある
- 文字化け品質判定に失敗
- 明示的名称ラベルはあるが値候補がない

DXF由来は `source=dxf_text` としてネイティブ抽出と区別し、値が競合した場合は自動上書きしない。

### 6. 印刷範囲を段階評価にする

- 生抽出文字は削除しない
- `inside=true` は第一候補
- `inside=null` は低信頼候補として保持
- `inside=false` は通常除外するが、名称未抽出時の診断件数へ残す
- 名称欄が見つからない場合だけ、不明領域を再探索する
- 枠、ビュー、文字の座標系が一致しているかを診断値として保存する

### 7. 辞書照合を正規化し、正式名称と分類語を分離する

- 照合前にNFKC、空白、英字大小、記号を同一規則で正規化する
- 部品名・ユニット名そのものは図枠欄や検証済みコメントから完全な文字列で保持する
- `PLATE`、`BASE` 等の辞書語は `part_type` や検索タグへ入れ、正式名称へ直接採用しない
- 客先別・装置別の複合名称辞書は、根拠資料とともに追加できるようにする
- 図面全体のどこかに一般語があるだけで名称確定しない

### 8. フォントと文字品質の証跡を追加する

- `SxGeomText.atr_word.font` と `font_name` をC# DTOへ保存する
- U+FFFD、制御文字、サロゲート、私用領域文字を別々に集計する
- 私用領域文字は推測置換せず、フォント依存の未解決字形として扱う
- CLI／workerの標準出力はUTF-8へ明示的に統一する
- JSON、DB、HTTP、画面の各段階で同じテスト文字列のコードポイントを検証する

### 9. 画面表示を安全側にする

- 名称未確定時は識別子を名称欄へ入れない
- `名称未抽出` と部品番号／モデル識別子を別列で表示する
- 名称候補がある場合は、候補値、取得元、信頼度、除外理由をレビュー画面へ出す
- 部品名辞書の一般語は正式名称ではなく分類候補として表示する

## 優先順位

1. 製品・装置・ユニット名称から `top_part.name`／ファイル名フォールバックを除去
2. 生文字を残したまま印刷範囲を段階評価し、全件除外を防止
3. 辞書照合のNFKC正規化と、正式名称・分類語の分離
4. 部品／ユニット／装置の名称フィールド分離
5. 空白入り名称ラベルの値切り出し修正と `UNIT Name` / `MACHINE Name` 誤採用防止
6. `top_part.comment` の名称候補化と、参照・変更説明の除外
7. セグメント種別・null内訳を記録するWindows再抽出診断
8. ICAD文字0件時のDXF補完
9. 限定条件付きの別文字要素ペア候補
10. フォント情報・私用領域文字の証跡追加
11. 既存39件の再正規化と名称レビュー

## 実装・再監査結果

調査後に抽出、正規化、API、2D/3Dビューワー表示を修正し、共有39件を再正規化した。

| 対象 | 改善前 | 改善後 |
| --- | ---: | ---: |
| 部品名称 | 33件中28件が未抽出 | 33件中5件が未抽出 |
| 製品・装置・ユニット名称 | 6件すべてが3D最上位名／ファイル名相当 | 5件を根拠付き名称として採用、1件は安全側で未抽出 |
| 図面番号 | 名称payloadに共通項目なし | 部品33件、製品・装置・ユニット6件の全39件で取得 |
| 3D最上位名の名称採用 | 製品・装置・ユニットで6件 | 0件 |
| 部品番号と図面番号の不一致 | 契約が分離 | 0件。部品では同一値 |

主な修正:

- `drawing_name`、`part_name`、`product_name`、`equipment_name`、`unit_name` のラベル規則を分離し、汎用 `name` を廃止した。
- ラベル内空白、全角英数字、辞書照合をNFKCで統一した。
- 名称ラベルと値が別文字要素の場合、名称欄に限定して同一ビュー・同一レイヤー・直近整列の値だけを採用する。通常の図枠配置に合わせて右側を優先し、最短要素が別ラベルなら遠方の文字へ飛ばさない。
- 図面番号は、図枠明示値、図面文字とファイル名の一致候補、ファイル名の順で決定する。`-00`のような全ゼロ管理付番だけ省略を許し、`-01`等の実体枝番は保持する。
- 部品名は明示2D名称、検証済み3D最上位コメント、ファイル名内の意味語、辞書候補を根拠付きで選ぶ。製品・装置・ユニットも対象別名称を優先する。
